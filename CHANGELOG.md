# Changelog

All notable changes to StuxAPIs' status page (status.stuxapis.net) are documented here.

Since v26.10.23 this project uses [Date Versioning](https://datevers.ing) (`YY.MM.DD`, the UTC release date, with `-1`, `-2`… for later releases the same day); earlier releases used Semantic Versioning.

## v26.11.08

### Changed

- Says the status is "checked regularly", not "every 5 minutes": the site description in `.githup.yml` and the README. GitHub runs the 5-minute schedule best-effort and often much less often; the status page itself now shows the real measured rhythm. The `.githup.yml` comment says the workflow asks for a check every 5 minutes, best-effort. The schedule itself is unchanged

## v26.11.07

### Added

- A FlashView monitor (flashview.stuxapis.net) in the StuxAPIs group, and FlashView in the README's list of what's monitored

## v26.11.06-1

### Added

- Monitors for every live StuxAPIs site, not just the services: the StuxAPIs website (stuxapis.net, which now
  answers) and StuxAPIs Services in the StuxAPIs group, and a new Templates group with StuxAPIs Soonpage,
  Maintenancepage, Servicepage and the GitHub Pages redirect. The note that stuxapis.net does not respond is gone;
  Lunar Calendar stays unmonitored until its site serves

### Added

- `.github/workflows/ci.yml`, running `bash tests/version.sh`, `python3 -c "import yaml; yaml.safe_load(open('.githup.yml'))"` on pushes to `main` and `test` and on every pull request

### Changed

- `commit.sh` and `commit.bat` end by saying to push `test` and open a pull request into `main`
- README (Versioning) and CONTRIBUTING (a new Branches section) describe the `test` branch flow: work and releases happen on `test`, and reach `main` only through a reviewed pull request that needs CI to pass

## v26.11.06

### Changed

- The page's logo and favicon are its own badge icon (the StuxAPIs mark with a heartbeat badge, as on
  services.stuxapis.net) rather than the plain StuxAPIs logo and icon. The README's header too, now titled
  StuxAPIs Status

### Fixed

- The changelog intro no longer also says the project follows Semantic Versioning

## v26.10.23

### Added

- `tests/version.sh`, which checks that `VERSION.md` is a valid Date Version, a real calendar date not in the future, and the same as the newest entry in this changelog

### Changed

- Switched from Semantic Versioning to [Date Versioning](https://datevers.ing): releases are numbered by their UTC release date as `YY.MM.DD`, with `-1`, `-2`… for later releases the same day. This release follows v1.0.3
- `commit.sh` and `commit.bat` refuse a `VERSION.md` that isn't a valid Date Version or is dated in the future (UTC), and warn when it's dated before today
- `README.md` and `CONTRIBUTING.md` describe Date Versioning and the release steps

## v1.0.3

### Changed

- The logos and icons in the Markdown docs (README and the like) follow GitHub's light or dark theme, using each brand's `logo-light`/`logo-dark` and `icon-light`/`icon-dark` files

## v1.0.2

### Added

- A GithubStats monitor (githubstats.stuxapis.net), now that its site is live

## v1.0.1

### Changed

- `max_response_time` raised to 15 seconds (GitHup's new default), so a slow but working site is no longer shown as degraded

## v1.0.0

### Added

- The StuxAPIs status page, built with GitHup and deployed to GitHub Pages at status.stuxapis.net
- Monitors for SeasonalOverlaysLibrary, Kittens and SecretGen (moved from status.stux.group) and the StuxAPIs media CDN
- Boring Legal Stuff hub with its six sub-pages, a 404 page, a sitemap and `robots.txt`, generated by GitHup
- A 5-minute check with `fill-gaps` (up to 4 checks, 5 minutes apart, when GitHub runs the schedule late), incident Issues, and an hourly rebuild
- `dev-server` (with `DEV_MODE` on by default and `--no-dev-mode`) and `commit` scripts
